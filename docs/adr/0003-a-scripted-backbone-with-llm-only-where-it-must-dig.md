# ヒアリングは骨格の木を軸にし、掘る場面だけ Claude に投げる

質問をすべてその場で生成すると、1問ごとに5〜60秒待つことになる。商談中の沈黙としては長い。
かといって事前に書いた分岐だけでは、想定外の答えを掘れない。よって**骨格の木で即答し、
掘り下げが要る場面だけ `sample` を呼ぶ**。どちらを使うかは**システムが決める**ので、
営業が選ぶ場面はない。

`sample` が使えないとき——営業が同意を断る、`use()` が `null` を返す、通信が不調——でも
**見積は出す**。掘り下げの精度は落ちるが、「この項目は後日確認」と記録が残る。
顧客の前で「使えません」と止まるのが最悪であり、掘り下げを必須にすると営業が客先で詰む。

## Consequences

- 骨格の木は、`pricingClass` が `foundation` の15件と必須項目6件を除いた**76件**に沿って組む。
  この21件は誰も選ばない基盤であり、質問してはいけない。選択項目から導かれる結論である。
- 76件すべてに質問を立てるのではなく、質問1つが複数項目を導く形（「お金のやり取りは
  ありますか」→ 決済・見積請求・会計連携）にして20〜30問に収める。取りこぼしは
  見積画面のツリーで調整する。
- 掘り下げの結果は用語表に落ちる。「承認フローが欲しい」を「部長1人が押す／2人が順に押す／
  金額で承認者が変わる」のどれかに確定させ、その意味を案件に書き残す。

## 訂正（2026-09-17）

当初この節には「選択項目37件に沿って組む」と書いていた。**この37件という数え方が誤り**である。
37件は「他のどの項目からも依存されていない項目」を数えたもので、`admin-ui`（管理画面）や
`pdf-generator`（PDF出力）や `role-permissions`（権限管理）は、他の項目がそれらに依存して
いるというだけの理由で外れていた。顧客はそれらを名指しで求める。

「何かに依存されている」と「営業が選ばない」は別のことだった。正しい区分はカタログが
すでに `pricingClass` として持っており、`foundation` の15件が本当に誰も選ばないものである。
